## 0. Rules for this work

These restate the pack's rules (`00-KICKOFF-PROMPT.md` section 5) plus lessons from this audit.

1. **Run real checks.** Never report a check, scan, or test as passing unless you ran it and kept
   the output. A recipe is done only when the **CLI** (`hardening audit` / `hardening check`)
   produces a real result on a real target. Adapter unit tests alone do not count.
2. **Never weaken a security test or rule to get green.** If a rule fires on SecHard's own code, fix
   the code or record an owner-approved exception. Do **not** narrow the rule until the finding
   disappears. Items F-08 (the narration rule was narrowed during the self-audit) and F-10 (the
   self-audit omitted a recipe) exist because this happened. [Correction 2026-10-11 per the plan
   review addendum, C-1: the original brief cited F-06 here; the narrowing incidents are F-08 and
   F-10.]
3. **No self-graded accuracy claims.** Detection rates must be measured on code the rule author did
   not write (item F-12). Report the numbers as measured, including misses.
4. **Security-relevant loosening needs owner review before merge.** That covers any change that lets
   more things pass: coverage requirements, severities, waiver rules, rule narrowing, exclusions.
   List each one in the checkpoint's owner review list.
5. **No real secrets anywhere.** Fixture secrets must be synthetic and composed at runtime (the
   repository's existing technique), so gitleaks does not flag the repository itself.
6. **SecHard never modifies the audited project.** Keep the tree-checksum test passing for every new
   recipe.
7. **Keep `docs/implementation-progress.md` and `CHANGELOG.md` accurate.** Watch every CI run to
   completion after each push.
8. **Do not push to `main` without the owner's go-ahead.** Work on a branch.

## Batch F1 — small fixes with large impact (do first)

### F-01 The `console.log` rule never fires in audit mode (bug)

**Evidence.**
- Audited a test app with `console.log` in `app/dashboard/page.tsx` and `app/api/login/route.ts`
  (the second logs a password).
- `results.json` recorded `2 console.log finding(s) outside production source directories were
  held back`.

**Cause.**
- `src/execution/recipes.ts`, `runQualityErrors`: it takes
  `(finding.location ?? '').split(/[/:\\]/)[0]` as the first path segment.
- Audit mode passes absolute locations (`/tmp/.../app/...`), so the first segment is `''`, which is
  never in `PRODUCTION_SOURCE_DIRS`.

**Fix.** Relativise the location against the audit/app root before taking the first segment.
Better, relativise every finding location at result creation (see F-15).

**Acceptance.**
- Add a regression test that runs the recipe against an **absolute** target path containing
  `app/x.ts` with `console.log`; the finding must be reported.
- A `scripts/x.ts` `console.log` must still be held back.

### F-02 Leaked secrets are mis-ranked, duplicated, and can be waived (security)

**Evidence.** On the test app:
- A Supabase **service-role** JWT in `lib/supabase.ts` (imported by a `'use client'` page) was
  reported as severity `unknown` with the generic gitleaks title "Uncovered a JSON Web Token".
- It appeared **twice per file**: once from the `gitleaks/repository` scan and once from
  `gitleaks/history`.
- The four duplicate rows ranked #7–10 in "Fix these first", below an unpinned GitHub Action at #5.
- A live-format Stripe secret key in `.env` did not appear in the top 10.
- Probe P7 (Appendix B): an exception scoped to that `unknown` secret finding on SEC-01 **waived
  it, and the gate passed**. The "critical findings can never be waived" rule did not apply because
  the severity was `unknown`.

**Fix.**
1. Classify secret findings in the gitleaks adapter, or a post-processing step:
   - **critical** for privileged or live keys: Supabase `service_role` (decode the JWT `role`
     claim, reusing the client-assets logic), `sb_secret_`, Stripe `sk_live_` and `rk_live_`,
     OpenAI, Anthropic, AWS, GitHub tokens, private keys, database URLs with passwords;
   - **high** for other credentials;
   - **low** for publishable or anon keys, which are informational.
2. Give each class a plain-English title and explanation, e.g. "Supabase service-role key exposed:
   it bypasses all row-level security".
3. De-duplicate findings across `gitleaks/repository` and `gitleaks/history`. Match on rule, file,
   and secret fingerprint. Keep one finding and note "also present in history".
4. Never allow a waiver on a secret finding that is critical or of unknown class. Add this to
   `policy/gate-policy.yaml` alongside the critical rule, enforced in the evaluator.
5. Rank "Fix these first" by severity × exposure. A secret in a client-reachable file or in
   committed history must outrank workflow hygiene.

**Acceptance.**
- In the test app (Appendix A), the service-role key and the Stripe live key are the top two
  "Fix these first" items, `critical`, one row each.
- Probe P7 now yields `satisfied=false` with a `waiver.forbidden` reason.

### F-03 "Mixed" controls pass on partial tool output with no manual evidence (security loosening)

**Evidence.**
- Batch W made `planner.ts` set `required_coverage: 'partial'` for `mixed` methods.
- 24 controls rely only on mixed methods, and none plans a manual check:
  CTX-01, GOV-01, AGT-01, AGT-02, AGT-03, DEP-02, SEC-01, CI-01, CI-02, QUAL-02, QUAL-08, QUAL-09,
  QUAL-11, QUAL-12, QUAL-13, AUTH-02, AUTH-03, DATA-01, WEB-01, BIZ-01, DEPLOY-01, OPS-01, REL-01,
  REL-02.
- Probe M1 (Appendix B): with every tool result `coverage: partial` and **no manual evidence**,
  these come out `satisfied`:
  - SEC-01;
  - CI-01 (isolated untrusted execution, satisfied by zizmor alone);
  - GOV-01;
  - WEB-01;
  - AGT-01.
- The implementation plan says: *"Mixed" means tool/test evidence **plus** reviewed
  manual/configuration evidence; it does not mean partial work can be silently accepted.*

**Fix.** For every `mixed` verification method, the planner must also plan a manual-evidence check
(recipe `<recipe>/review` or the control's declared manual recipe). The control is satisfied only
when the tool check passes, at partial or better, **and** current manual evidence exists. Where a
tool truly gives complete coverage, reclassify the method `automated` and require complete.

**Acceptance.**
- Probe M1 shows those controls `unmet` with `manual.missing`.
- Supplying current manual evidence for them makes them `satisfied`.
- List this change in the owner review list.

### F-04 A taint-mode security rule pack

SecHard ships only 9 security rules. Add a reviewed opengrep pack using `mode: taint` with sources
from request data:
- `req.query`, `req.body`, `req.params`;
- `searchParams.get(...)`, `request.nextUrl`, `await req.json()`;
- `formData.get(...)`;
- Python `request.args`, `request.form`, `request.json`.

Cover these sinks:

| Rule | Sinks |
| --- | --- |
| SQL injection | `pool.query`, `client.query`, `db.execute`, `sequelize.query`, `knex.raw`, Prisma `$queryRawUnsafe`, Python `cursor.execute` with f-strings or `%` |
| XSS | `dangerouslySetInnerHTML={{ __html: <tainted or DB-sourced> }}`, `innerHTML`, `document.write` |
| SSRF | `fetch`, `axios.*`, `got`, `node-fetch`, `http(s).request`, Python `requests.*` (replace the regex-only rule) |
| Path traversal | `fs.readFile*`, `fs.createReadStream`, `path.join` into fs, `send_file` |
| Open redirect | `NextResponse.redirect`, `res.redirect`, `redirect()` with tainted URL |
| Command injection | `exec`/`execSync` with tainted string; Python `subprocess(..., shell=True)` |

Treat `dangerouslySetInnerHTML` with **any** non-literal value as at least a medium finding, even
without taint.

**Acceptance.**
- Each rule has a vulnerable fixture **including the variable-assignment shape**
  (`const u = searchParams.get('url'); fetch(u)`) and a fixed twin.
- The pinned opengrep binary detects the vulnerable fixture and stays silent on the fixed one,
  through the CLI.

### F-05 Pattern rules for common vibe-coded mistakes

Each rule needs vulnerable and fixed fixtures:
- weak password hashing: `createHash('md5' | 'sha1')` applied to a value named password or pwd;
- JWT problems: `algorithm: 'none'`; `algorithms` containing `'none'`; a hardcoded string literal as
  the `jwt.sign` or `jwt.verify` secret;
- insecure cookies: `cookies.set`/`res.cookie` with `httpOnly: false` or `secure: false`, or without
  them on a session cookie;
- CORS: `Access-Control-Allow-Origin: *` together with `Allow-Credentials: true`; `cors({ origin:
  true, credentials: true })`;
- weak randomness: `Math.random()` used for tokens, IDs, resets, or OTPs (variable or function name
  heuristic);
- logging secrets: `console.*` or a logger receiving a variable named password, token, secret, or
  apiKey;
- OpenAI or Anthropic SDK constructed in a `'use client'` file, or with
  `dangerouslyAllowBrowser: true`;
- dangerous Next.js config: `productionBrowserSourceMaps: true`, `typescript.ignoreBuildErrors:
  true`, `eslint.ignoreDuringBuilds: true`;
- zizmor's `excessive-permissions` and `permissions: write-all` must surface. Check why they did not
  on the test workflow.

### F-08 Narration-comment rule recall

`src/quality/tells.ts` requires two identical identifiers shared between a comment and the next line.
That catches 1 of about 12 typical AI narration comments, such as:
- `// Fetch the data from the API` above `axios.get(...)`;
- `// Query the database for the user` above `pool.query(...)`;
- `// Render the AI response` above `return <div ...>`.

Improve recall without returning to false positives on genuine "why" comments:
- verb-and-object restatement using synonym sets (fetch/get/load, query/select, render/return
  JSX, check/if, add/push, create/new);
- a "comment above almost every statement" density signal per function;
- generic helper headers ("Helper function to …", "Utility to …", "This function …").

Keep `RATIONALE_MARKERS` as the exemption.

**Acceptance:** the measured recall on Appendix A narration comments is at least 0.7, with zero
findings on SecHard's own rationale comments. Do not achieve the second by narrowing the first.
