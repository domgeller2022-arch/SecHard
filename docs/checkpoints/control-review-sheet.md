# Control review sheet

One row per control for owner review.

Review state: 0 draft, 35 owner-reviewed. Whether a definition is
approved is decided by a resolving record in `controls/approvals.yaml`, not by the definition's own
`review_status` field: the record names the reviewed-content digest, so an edit invalidates it.

## What to check on each row

1. Does the applicability condition match when you would actually want this control?
2. Is each acceptance criterion testable, or is it a wish?
3. Is the stated verification method real, or aspirational? A method with no implemented recipe
   must be `manual_only` until the recipe exists.
4. Are the limitations honest about what the method does not cover?
5. Is a control missing entirely from your threat model?

## How to record approval

1. Run `node dist/cli.js approvals --policy .` to print each definition's reviewed-content digest.
2. For each definition you accept, add a record to `controls/approvals.yaml` naming the control,
   its definition version, the exact digest, your identity, the date, and `kind: owner` (or
   `kind: independent` when someone other than the author reviewed it).
3. Re-run `approvals` to confirm the record resolves. An edited definition changes the digest and
   the approval stops applying; that is intended.

A batch continuation message is not approval of these definitions. Only the owner records these
records, and a sole maintainer's acceptance is self-review, reported as such.

## Deviations from the blueprint

Acceptance criteria were written concisely from blueprint section 6 rather than copied verbatim.
No control was added, removed, or merged. Per-control wording is in `controls/controls.yaml`.
The `related_risk` mappings are the only change of substance: no exact standards requirement IDs
are asserted anywhere, because no mapping has been reviewed against a pinned source edition yet.
